# 页面矩阵、素材、内容与建站

> 2026-10-25 定稿。对照「游戏站建站全流程清单」第 5–8 部分（节点 22–34）。
> 本文是**判断标准 + 产物规格**：怎么写、写多少、什么算过、什么必须退回。
> 操作步骤见 `SOP-游戏攻略站上线.md` 与 `.claude/skills/build-game-site.md`；
> 岗位卡见 `docs/agents/03/04`（建站协调员）、`05/06`（QA）、`13/14`（关键词研究员）。
> 方法论对照与取舍记录见 `docs/RESEARCH-生财手册内容生产对照.md`。

## 一、三条原则（先记住，再看细则）

1. **页面唯一依据是搜索需求**。一个搜索意图 = 一个内页；
   MUST NOT 为「看起来完整」建没人搜的页面。
2. **AI 只做过滤与整理，不做凭空生成**。事实必须能指到来源；
   指不到就标 `[Unconfirmed]`，或不做这一页。
3. **批量是放大器，不是遮羞布**。单页做不扎实，批量只会批量生产垃圾；
   批量的前提是「能稳定做好一个内页」。

## 二、页面矩阵（节点 22–24）

### 2.1 产物：内页清单表

每个可建站 MUST 在开工前产出 `keyword-results/{slug}-matrix.md`，
由关键词研究员交付、建站协调员核对、候选分析员可复核。表头固定：

| 页面名（slug） | 目标搜索词 | 搜索意图 / 要回答什么 | 页型 | 优先级 | 素材源（≥2） | 目标词数 |
|---|---|---|---|---|---|---|

规则：

- **一个搜索意图只占一行**；同一意图的不同说法合并到搜索量最大的那个词
- 每行 MUST 有 `目标搜索词` 与 `搜索意图`；两列写不清的行直接删除
- `页型` 取值：`codes` / `beginner` / `tier-list` / `boss-or-mechanic` / `faq` / `nav`
- `优先级` 取 `P0`（首批必做）/ `P1`（30 天内）/ `P2`（按数据再加）
- `素材源` MUST 至少 2 个，且至少 1 个官方源（见第三节）
- 矩阵是**任务清单，不是一次做完的承诺**；首版只做 P0 前 5–8 行

示例（两行）：

```markdown
| 页面名（slug） | 目标搜索词 | 搜索意图 / 要回答什么 | 页型 | 优先级 | 素材源（≥2） | 目标词数 |
|---|---|---|---|---|---|---|
| witchspire-codes | witchspire codes | 现在能用的兑换码 + 怎么兑换 | codes | P0 | 官方 Discord 公告；Steam 公告 | 1,200 |
| lumi-boss-guide | witchspire lumi boss how to beat | Lumi 二阶段怎么打、弱点与配装 | boss-or-mechanic | P0 | 官方视频；2 篇社区攻略 | 1,500 |
```

### 2.2 分组规则（MECE）

矩阵必须同时满足：

- **相互独立（ME）**：不同分类不互相包含（`Guides` 与 `Beginner Guides` 不能并列）；
  同一分类下不得出现同义词或单复数重复
- **完全穷尽（CE）**：一个分类下覆盖该分类的已知需求，且按流量从大到小排
- **禁止大空类**：`gameplay` / `general` / `tips` 这类不能作为分类名
- **Codes 类只放一个关键词**（`{game} codes`），不拆「最新码 / 过期码」两页
- 非英文词先翻译成英文再入表；只允许改拼写错误，**禁止扩写**

> 组内结构：先按「玩法系统 / 内容类型」分 MECE 类，再在每行标 P0/P1/P2；
> P0/P1 是**执行顺序**，不是分类维度。

### 2.3 页型与数量

首批 5 类页型是**候选池，不是必建清单**——某类没有对应搜索词就不建，用同优先级长尾页顶上：

| 页型 | 说明 | 典型词 |
|---|---|---|
| `codes` | 兑换码（只做一页，持续更新） | `{game} codes` |
| `beginner` | 前 2 小时怎么玩 | `{game} beginner guide` |
| `tier-list` | 角色/武器/职业排行 | `{game} tier list` |
| `boss-or-mechanic` | 卡点内容：Boss、核心系统 | `{game} {boss} how to beat` |
| `faq` | 发售/平台/联机/价格等事实问答 | `is {game} multiplayer` |

数量口径：

| 时点 | 标准 |
|---|---|
| 首批（上线） | **5–8 页**，5 类页型尽量各 ≥1；总词数 ≥ 8,000；单篇 ≥ 1,200 |
| D+30 | **≥ 15–20 页**（下限）；原「每周 +5–10 页」节奏不变，超出下限按 A/B 档排优先级 |
| D+90（A/B 档） | **30–50 页**，按 GSC 搜索词补齐长尾 |
| C/D 档 | 不再新增；D 档按止损规则停止投入 |

规则：

- 首批 5–8 页是**速度与深度的平衡点**，MUST NOT 为了抢窗口降到 3–4 页
- 数量不是目标，**独立搜索意图数**才是；两页可互换 intro 的必须合并
- 攻略数超过 25 篇后仍可加，前提是每篇有独立意图、无主题重叠

### 2.4 长尾覆盖检查（节点 24）

- **P0 词必须 1:1 有落地页**；覆盖率 = 有落地页的 P0 词 ÷ P0 词总数，**必须 100%**
- P1 词覆盖率 D+30 ≥ 70%；未覆盖的词 MUST 在矩阵里保留，不许删行假装完成
- 检查脚本：`node scripts/keyword-coverage.mjs --slug <slug>`（加 `--check` 时 P0 未 100% 退出码 1）；
  脚本按「页 slug 相同」或「目标词实词全部出现在该页 slug/title/keywords」判定命中，并列出矩阵外页面
- 未达标处理：先补页，不许用「页面已覆盖相关主题」糊过去

## 三、素材（节点 25–26）

### 3.1 双源规则（硬约束）

**每一页 MUST 至少 2 个独立来源，且至少 1 个官方来源。**

| 层级 | 来源 | 可用作 |
|---|---|---|
| A 官方 | Steam 商店页、开发商官网、官方公告（含 Demo/Playtest 独立 appid 的公告流）、官方视频、官方 Discord 公告 | 直接事实 |
| B 社区 | 高播放/近期 YouTube 视频字幕、Steam 评测、Reddit 讨论、Fandom/独立 wiki | 需与 A 交叉，或标 `Community` |
| C 媒体 | 游戏媒体评测、预览 | 需与 A 交叉，或标 `Editorial` |

不被接受为事实来源的输入（MUST NOT 当依据）：

- Google 搜索建议（只证明「有人在搜」，不证明「事实是什么」）
- 竞对攻略站的正文（结构可参考，文字与数据不可引用）
- 其他站的既有内容（跨站污染）
- 模型记忆 / 常识推断（无链接即无来源）

### 3.2 素材文档

每站 MUST 有 `keyword-results/{slug}-sources.md`，按关键词分节，每节固定格式：

```markdown
## {关键词}

### 来源 1：{A/B/C} — {URL}
- 抓取日期：YYYY-MM-DD
- 关键内容：（原文摘录或要点，保留数字与专有名词原样）

### 来源 2：{A/B/C} — {URL}
- 抓取日期：YYYY-MM-DD
- 关键内容：…
```

规则：

- MUST 记录 **URL + 抓取日期**；无日期的来源视为无效
- 数字、专有名词 MUST 原样摘录，不许「大意转述」
- 两个来源冲突时：以官方为准并记录冲突；官方也没有 → 写 `[Unconfirmed]`，MUST NOT 二选一当事实

### 3.3 素材不足时的三种处理

1. **降级**：只写能核实的部分，未核实的标 `[Unconfirmed]`（英文站用英文标记）
2. **换来源**：换关键词或换来源面（如补 Demo appid 公告、补官方视频字幕）
3. **不做这页**：连降级都撑不起 1,200 词，就从矩阵删行，MUST NOT 用空话凑数

> 素材不足是**选题问题**，不是写作问题；靠写作技巧补素材 = 编造的前兆。

## 四、内容（节点 27–30）

### 4.1 写作规格

| 项 | 标准 | 检查方 |
|---|---|---|
| title | 含目标关键词，**40–60 字符** | QA + 构建门禁 |
| meta description | 含关键词，**140–160 字符** | QA + 构建门禁 |
| H1 | **有且仅有 1 个** | 构建门禁 |
| 标题层级 | H2 分节，H3 不跳级 | 构建门禁 |
| 首段 | **40–60 词直接给答案**，不绕弯 | QA 抽样 |
| 正文词数 | **≥ 1,200 词**（FAQ 类可 800，同批平均仍要 1,200） | QA 逐页统计 |
| 段落 | 每段 3–4 句，适合扫读 | QA 抽样 |
| 表格 | 每页 2–4 个 | QA 抽样 |
| 结构化数据 | FAQ 类带 FAQPage | QA 抽样 |
| 事实标注 | 每个数字有来源或 `[Unconfirmed]` | QA 全量检索 |

> **长度规则只约束「新写或本次修改」的页面，存量页不追溯。**
> 实测 45 站 1,078 篇：description 中位数 194 字符、**91.7%（988 篇）超过 160**；
> title 中位数 64 字符、59%（637 篇）超过 60。全量返工无收益——SERP 只是截断显示，不影响收录。
> 存量页超长记为「可选优化」，**不判 FAIL**；本次新增/修改的页面 MUST 按 40–60 / 140–160 写。

### 4.2 生成流程（固定五步）

```
矩阵（P0 前 5–8 行）
→ 素材（每页 ≥2 源，写进 {slug}-sources.md）
→ 固定提示词（结构 + 红线，同类页共用一份）
→ 分批生成（同类 ≤5 篇/批）
→ 逐篇自检 + QA（100% 自动化事实检索，≥30% 人工抽样）
```

规则：

- MUST 先有矩阵行再写页；MUST NOT 边写边想选题
- MUST 先有素材再让模型写；**素材文档就是输入**，不允许模型自由补事实
- MUST 用同一份提示词产出同类页，保证格式与质量稳定
- **每批 ≤5 篇同类**；塞多了质量下降（手册实测，我们沿用）
- 每批产出 MUST 逐篇过一遍再进内容目录；MUST NOT 攒 20 篇一起交 QA

### 4.3 批量红线（出现任一条即 FAIL）

- 同一模板句式换个游戏名/角色名批量复制
- 页面内容与目标关键词意图不匹配（搜 codes 给玩法介绍）
- 一页里塞多个意图（codes + tier list + beginner 混写）
- 为凑页数把同一意图拆成多页（内容自噬）
- 未核实数字/角色名/兑换码写成确定事实

> 判断标准：**你能稳定把「一个」内页写成真实、有用、玩家愿意看的内容，才允许批量**。

### 4.4 related / sources 规范

- `related` MUST 用**块状数组**（内联数组会被静默忽略）
- `sources` MUST ≥1 条 `Official` 层；其余按 A/B/C 分级渲染
- 每条 source MUST 是可达链接；死链等于没有来源

### 4.5 内容合规口径（2026-10-25 起）

- 事实红线不变：不编造、数字标来源、与 Steam/官方一致
- AdSense 专项审计**暂缓**；`ca-pub` 新站不注入、存量不动
- 英文站中文标记 MUST 全部改为英文（`[Unconfirmed]`）
- 信任页（privacy / terms / about / contact）继续保留，服务 Adsterra 与 SEO

## 五、建站（节点 31–34）

### 5.1 三层分离（模板成立标准）

| 层 | 内容 | 换新站时 |
|---|---|---|
| 框架层 | `app/` 布局与路由、`components/`、`lib/guides.ts`、`lib/metadata.ts`、`lib/schema.ts` | **不改** |
| 配置层 | `lib/seo-config.ts`（站名/域名/GA/GSC）、`lib/adsterra-zones.ts`、导航分类、主题色 | 只改值 |
| 内容层 | `content/guides/*.md`、`content/home-content.md`、各语言文案 | 整层替换 |

**验收方法**：换一个游戏名，只动配置层 + 内容层就能整站切换 → 模板成立；
需要改框架层才跑得起来 → 模板不合格。

### 5.2 模板来源（节点 31）

- 现状：`templates/wiki-base/` **已建成**（2026-10-26），一条命令生成新站
- 生成：`node scripts/new-site.mjs --slug <slug> --name "<官方写法>" --developer … --publisher … --release-date YYYY-MM-DD [--steam-id …]`
  - 目录名 = `<slug>wiki`；默认域名 `<slug>wiki.vercel.app`
  - 脚本替换 `{{SITE_NAME}}` / `{{GAME_NAME}}` / `{{DOMAIN}}` / `{{DEVELOPER}}` / `{{PUBLISHER}}` /
    `{{STEAM_URL}}` / `{{RELEASE_DATE}}` / `{{SITE_DESCRIPTION}}` / `{{GENRE_LINE}}`；
    只要还有 `{{UPPER_SNAKE}}` 残留就以退出码 1 结束
- 新站 MUST 从模板生成，MUST NOT 从在运营站复制；手抄运营站会把历史内容、广告代码、旧 GA 一起带过来
- 模板刻意留空：`content/guides/`（只有 `.gitkeep`）、`app/faq` 与 `app/tier-list` 的问答/榜单数组、
  `lib/adsterra-zones.ts`、`lib/seo-config.ts` 的 GA/AdSense ID —— 这四处 MUST 有可核验来源后再填
- 首页「Start Here」直接读 `content/guides/*.md` 取最近 6 篇，新增页面不用改首页
- 模板 V2 的设计参考池：**5–10 个 DR≈0 且排名靠前的新站**，
  只提炼结构/导航/排版/配色；MUST NOT 抄文字与数据（抄结构不抄内容）
- 模板差异化仍暂缓：当前只维护一套模板，V2 在流水线跑顺后再做

### 5.3 必建文件

以 `.claude/skills/build-game-site.md` 的 12 项清单为准，其中 MUST 存在的有：

- `app/layout.tsx`、`app/page.tsx`、`app/faq/page.tsx`、`app/tier-list/page.tsx`
- `app/guides/[slug]/page.tsx` + `content/guides/*.md` + `lib/guides.ts`
- `app/sitemap.ts`、`app/robots.ts`、`app/favicon.ico`（或多尺寸 icon）
- 信任页 4 个：`privacy` / `terms` / `about` / `contact`
- `lib/seo-config.ts`、`lib/metadata.ts`、`lib/schema.ts`
- `vercel.json`（`installCommand: pnpm install`）、`pnpm-lock.yaml`

### 5.4 构建门禁（节点 34）

MUST 全部通过才允许部署：

1. `pnpm install && pnpm build` **exit 0**
2. 静态检查（脚本化，缺脚本时人工核对并留证据）：
   - 每页 title 40–60 字符、description 140–160 字符
   - 每页**有且仅有 1 个 H1**，H2/H3 不跳级
   - 除首页外页面 canonical 指向自身
   - sitemap 条目数 = 实际页面数
3. 残留扫描：他站游戏名 / 域名 / Hugo shortcode / 模板文案 **0 命中**
4. 抽查 PC 与手机宽度（375px）无空白、错位、横向溢出
5. `content/guides/*.md` frontmatter 的 `related` 为块状数组、`sources` ≥1 Official

> 构建通过只证明「能跑」，不证明「内容对」；内容对由 QA 判（`docs/agents/05/06`）。

## 六、数据驱动补页（与阶段十一的接口）

内容生产不是写完就结束，GSC 的新词就是下一批页面。

### 6.1 复盘看五个数

展示量 / 点击量 / 平均排名 / 平均点击率 / **搜索词报告**（最重要）。

### 6.2 信号 → 动作

| 信号 | 动作 |
|---|---|
| 新搜索词有展示、站内无对应页 | **补页**（进矩阵 P1，每次复盘 2–3 页） |
| 某页表现好 | 围绕它做关联内容（同系统/同 Boss/同角色） |
| 有展示无点击 / 排名 11–30 | 改 title/description 与首段，不新开页 |
| 页面未收录 | 先查技术（sitemap/canonical/内容量），改完重新提交 |
| 上线 3 周仍个位数访问、无展示 | 评估换词（与 D 档止损分开：D 档看 90 天，换词看内容是否回答了需求） |

规则：

- **补页优先于开新站**：已有站有展示、缺页，先补这个站
- 补页 MUST 有 GSC 搜索词或明确长尾词证据，MUST NOT 凑数
- 每次复盘 MUST 产出 2–3 个具体补页任务（页面名 + 目标词）

## 七、各节点的审核方式

| 节点 | 审什么 | 证据 | 谁审 |
|---|---|---|---|
| 22 分组 | MECE 是否成立、有无大空类 | `{slug}-matrix.md` 分类表 | 候选分析员 + 主 Agent |
| 23 页面结构 | 每页是否有独立搜索意图 | 矩阵每行的「搜索意图」列 | 建站协调员 |
| 24 长尾覆盖 | P0 覆盖率是否 100% | 矩阵 ↔ 站内页面清单对照 | QA |
| 25 事实源 | 每页素材是否 ≥2 源且 ≥1 官方 | `{slug}-sources.md` | QA |
| 26 事实核验 | 数字/专名是否可追溯 | QA 的语料零命中检索结果 | QA |
| 27 生成流程 | 是否先矩阵后内容 | 矩阵文件 + 内容目录提交顺序 | 主 Agent |
| 28 内容量 | 页型 + 词数是否达线 | QA「页型 + 词数」表 | QA |
| 29 related/sources | 块状数组、≥1 Official、无死链 | 构建输出 + 链接抽查 | QA |
| 30 合规检查 | 有无编造、中文标记泄漏 | QA 审计报告 | 合规审计员 |
| 31 模板来源 | 是否从模板目录复制 | `git diff` 的初始提交 | 主 Agent |
| 32 必建文件 | 12 项是否齐全 | build-game-site 清单勾选 | QA |
| 33 依赖字体 | pnpm + geist 自托管 | `package.json` / `vercel.json` | 主 Agent |
| 34 构建门禁 | build exit 0 + 静态检查 | 构建日志 + 检查脚本输出 | 主 Agent |

三条通用原则：证据链优先；脚本先跑人后看；异常必须显性（缺数据写 `[待确认]`，不许静默通过）。

## 八、待验证（2026-11-25 复盘）

| 项 | 验证方式 |
|---|---|
