> 需求：重点站（PV>1000）每天根据用户反馈/搜索/抱怨精写，不设轮换、不排队。

## 二、每日扩充规则（2026-09-02 起）

- **名单内每站每天 1 篇**，不再 round-robin 排队
- 每站各自走完整流程：反馈采集 → 选题 → 写 1 篇 → QA → 部署
- **并行执行**：每 1-2 站一个子 Agent 并行处理（沿用 coordinator 多站并行调度规则）；全部完成后统一 commit
- **跳过规则**：某站当天无可用素材（无新反馈 / 无未被覆盖的高频问题）→ 该站记录跳过原因到 `.agent/expand-daily.json`，**次日优先补该站**；MUST NOT 无素材硬写
- ~~每周每站最多 2 篇~~（已取消，2026-09-02：改为每站每天 1 篇）
- 名单状态记录在 `.agent/expand-daily.json`（含每站上次扩充日 + 跳过记录）

## 三、每日流程（05:00 coordinator 内执行）

```
Step 1 读取扩充名单（.agent/expand-daily.json）
Step 2 对名单内每个站（每 1-2 站一个子 Agent 并行）：
       ├─ 反馈采集（反馈分析师 quick，10-15 分钟/站）
       │    ├─ Steam Community 讨论区（该游戏）
       │    ├─ Reddit r/{game}
       │    ├─ Steam 评测（负面优先，信息量最大）
       │    └─ 可用时：GSC 搜索查询（凭据解决后接入）
       ├─ 问题选择（MUST 满足全部条件）
       │    ├─ 高频：≥3 条独立来源提及
       │    ├─ 具体：可写成一篇文章的具体问题
       │    └─ 缺口：未被已有攻略覆盖（先查现有 slug 列表）
       ├─ 写 1 篇攻略（建站协调员 expand 模式）
       │    ├─ 800-1500 词，问题导向标题（How to / Why）
       │    ├─ sources 三层标注（Official/Community/Editorial）
       │    ├─ 反馈事实 MUST 可追溯（保留来源链接）
       │    └─ [Unconfirmed] 英文标记
       ├─ QA quick（残留扫描 + 编造检查）
       └─ 部署（该站）
Step 3 记录 + commit + 推送（expand-daily.json / build-history.json / STATS）
```

## 四、岗位分工（复用现有 8 岗位）

| 环节 | 岗位 |
|------|------|
| 反馈采集 | 玩家反馈分析师（17/18） |
| 选题+写作 | 建站协调员（03/04） |
| QA | QA 审核员（05/06） |
| 记录收尾 | 主 Agent（coordinator） |

## 五、质量红线（MUST）

- MUST 基于真实反馈（帖子/评测/讨论），MUST NOT 编造用户声音
- MUST 与已有攻略查重（内容自噬红线）
- MUST 每篇独立搜索意图（不同问题）
- MUST 所有数字标注来源或 [Unconfirmed]
- MUST 每篇 800-1500 词（精写不凑数）
- **每日 5 篇是节奏上限，宁缺毋滥**：素材不足时跳过优于硬写；任何一天不得为凑数牺牲质量

## 六、记录与验收

- `.agent/expand-daily.json`：名单内每站上次扩充日 + 跳过记录
- 每篇扩充写入 `build-history.json`（mode: "expand-feedback"）
- 每周汇总：周报列出每站新增篇数 + 来源问题类型
- 验收：PV 变化在 2 周后由监控员评估（扩充是否带来流量增长）

## 七、与现有定时任务的关系

05:00 coordinator 每日执行顺序：
1. **MUST 先做内容扩充**（本计划：所有 PV>1000 站各 1 篇，并行）— 高流量站维护优先
2. 再做建站/侦察（每天最多 1 新站）— 扩张其次
3. 汇总 + commit + 部署

若单日工作量过大（超时风险），扩充与建站分两批 Agent 串行执行；扩充阶段每完成若干站 commit 一次，防长跑中断丢工作。
