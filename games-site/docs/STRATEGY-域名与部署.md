## 二、域名（节点 17）

### 2.1 现状与决策

- 45 个 wiki 站全部使用 `{project}.vercel.app`
- 站点 canonical 写在 `<site>/lib/seo-config.ts` 的 `SITE_CONFIG.url`
- 台账「站点」列写的就是这个域名（裸域名，不带 `https://` 与结尾斜杠，如 `witchspirewiki.vercel.app`）

**决策：维持子域，暂不买自有域名。**

### 2.2 已知风险（记账，不是待办）

| 风险 | 说明 |
|---|---|
| URL 绑定托管账号 | `{project}.vercel.app` 全局唯一且归属当前 Vercel 账号；换账号 / 换托管平台，URL 无法保留 |
| 迁移代价高 | 换 URL = 索引与排名重新积累；没有 301 就无法保住存量信号 |
| 品牌与信任弱 | Adsterra 接受子域，但独立域名在 CTR、品牌记忆、后续 AdSense 上都更好 |
| 续费陷阱 | 10–15 元/年通常是首年促销价，**续费价远高于首年**；按 150 个/月算，第二年才是真成本 |

### 2.3 将来要迁自有域名时（playbook）

只在决策改为「买域名」后执行：

1. **只给通过 D+30 索引检查的站买**（GSC 收录 ≥50%）——不给还没验证的站付钱
2. 新域名先绑到现有 Vercel 项目，子域保持可访问
3. 全站 `SITE_CONFIG.url` / canonical / sitemap 切到新域名
4. **子域 301 到新域名**，观察 30 天
5. GSC 提交「地址更改」，确认新域名收录

MUST NOT 在**没有 301** 的情况下直接换 URL。
MUST NOT 批量买域名后再慢慢建站（续费从购买日算）。

## 三、Vercel 项目与账号（节点 18）

### 3.1 现状

- **单账号 Hobby**，45 个项目
- 项目创建：`vercel link --project <name> --yes`（手动）
- 部署：`./deploy-wiki-site.sh <site-dir>`（CLI 直传，`rootDirectory` 必须为空）
- 部署日志：`.agent/deploy-log.jsonl`

### 3.2 官方限额（2026-09-14 版文档）

| 项 | Hobby | Pro |
|---|---|---|
| 项目数 | 200 / 账号 | 无限 |
| 部署 | 100 次/日 | 6,000 次/日 |
| 商业用途 | **禁止**（仅限非商业个人使用） | 允许 |

### 3.3 已知风险

1. **商业用途冲突**：已有 36 个站挂 Adsterra，属于商业用途，与 Hobby「非商业个人使用」条款冲突。
2. **多账号分摊属于规避限制**：官方公平使用条款明确把「规避或滥用限制」列为违规。
   按 75 站/账号新开免费账号，技术上能把日部署压到 100 以下（45 站批量日实测 34–42 次，
   线性推算 75 站约 57–70 次），但改变不了商业用途的性质。
3. **连带失效**：账号被暂停时，该账号下全部站点与 `*.vercel.app` URL 一起失效。

### 3.4 复盘时三选一

| 方案 | 现金 | 部署能力 | 合规 | 备注 |
|---|---|---|---|---|
| **A. Vercel Pro** | $20/月 | 6,000 次/日、无限项目 | ✅ | 单账号即可，不用拆；约 1 元/站/月（按 150 站） |
| **B. Cloudflare Pages** | 0 | 500 构建/月、100 项目/账号 | ⚠️ 条款未禁止商业（也无明文许可） | 需先改静态导出；150 站/月约 2 个账号/月 |
| **C. 维持 Hobby + 75 站/账号** | 0 | 100 次/日/账号 | ❌ | 商业用途 + 规避限制；不推荐 |

Cloudflare 的可行性前提：45 个 wiki 站都是 SSG（`generateStaticParams`、无 API 路由、
无 `next/image`），改 `output: 'export'` 后可以承接；但必须先在 1 个站跑通构建、
sitemap、路由和 404，再谈批量。

### 3.5 复盘触发条件

满足任意一条就提前复盘，不等 11-25：

- 单日部署连续 3 天 > 80 次
- 收到 Vercel 限额 / 条款警告，或项目被暂停
- 站点数 > 150 且仍保持 5 站/天节奏

### 3.6 项目创建（当前仍是手动）

```bash
cd <site-dir>
vercel link --project <project-name> --yes
```

MUST NOT 设置 `rootDirectory`（CLI 直传模式下会导致路径叠加，见部署脚本头注释）。

## 四、GA4（节点 19）

### 4.1 当前流程（人工 + 每日回填）

1. GA 后台建 Property + Web Stream，URL 填部署后的域名
2. 记下 `G-XXXXXXXXXX`（Measurement ID）和纯数字 Property ID
3. **把两个 ID 填进飞书「站点台账(人工)YYYY-MM」对应行的
   `GA4-measurementID` / `GA4-propertyID` 两列**（2026-10-26 起的主路径）
   —— 每天 20:00 的 `sync-ledger-manual.mjs` 会自动写进站点与 Dashboard
4. **GA 管理 → 媒体资源访问权限 → 把 Dashboard 服务账号加为读取者**
   （不加 = GA4 有数据但 Dashboard 永远读不到）

手动兜底（当天就要生效、或台账写不进去时）：
把 ID 写进 `.agent/ga4-ids.json` 后执行
`node scripts/set-ga4-ids.mjs .agent/ga4-ids.json`；脚本做的是同一件事
（改站点 `lib/seo-config.ts` + 维护 `dashboard/lib/sites.ts`）。

### 4.2 已知限制与风险

- GA4 单账号上限 **2,000 个 Property**（官方结构限制）；按 150 站/月约 13 个月需要第二个 GA 账号
- 手动建 property 是 5 站/天节奏下最容易漏的一步；漏了 Dashboard 就缺站
- 查不到 / 没建好时写 `[待确认]`，MUST NOT 编造 GA ID
  （`[待确认]` 行会被回填脚本跳过，Dashboard 的空值过滤也不会把它当数字）

### 4.3 自动化（暂缓，不实施）

将来可走 GA Admin API：

- `properties.create` 建媒体资源
- `dataStreams.create` 建 Web Stream
- 需要 GCP 服务账号 + `analytics.edit` 权限，并把服务账号加到 GA 账号

用户 2026-10-25 决定**先保持手动**，后续再安排。本文只记录方案，不落地脚本。

### 6.3 重新开启的条件（不设日期）

## 八、站点台账：两张表 + 每日回填（2026-10-26 起）

### 8.1 为什么拆

原来的「站点台账2026-10」混着两类东西：脚本算出来的指标（PV、环比、分级、攻略数）
和只有人能做的事（GA4 ID、GSC 提交、Adsterra 广告代码）。混在一张表里，
程序没法判断「哪些是人工还没做」，人也分不清「哪些格子不该自己填」。

拆成两张，一张一对作者：

| 表 | 表名 | 谁写 | 内容 |
|---|---|---|---|
| 自动化 | `站点台账(自动化)YYYY-MM` | 脚本 | PV(30d)、PV 环比、攻略数、广告位上线数、生命周期状态、建站成本… |
| 人工 | `站点台账(人工)YYYY-MM` | 人 | GA4 ID、GSC 状态、三个广告位代码（另有两列由脚本同步：上线日、自动化状态） |

**填上 = 人工做完了**。这是人工表唯一的心智模型，不需要额外的状态字段。
最后一列 `自动化状态` 是**程序回写**的镜像：人工看这一列就知道「我填全了、程序也确实落地了」。

### 8.2 人工表的列

| 列 | 含义 | 程序动作 |
|---|---|---|
| 站点 | **裸域名**（`witchspirewiki.vercel.app`，不带 `https://`、不带结尾斜杠）= 主键 | 脚本用 `siteDirOf()` 反推目录名定位站点；域名也直接从这里取，不再单列 |
| 上线日 | 从 `站点台账(自动化)` 同步来的上线日期 | **程序同步**：每轮比对，空着或对不上就写回；用来区分「新站还没来得及填」和「老站漏了」 |
| GA4-measurementID | `G-XXXXXXXXXX` | 回填 `lib/seo-config.ts` |
| GA4-propertyID | 纯数字 | 回填 `dashboard/lib/sites.ts` |
| GSC | 填「是/已完成」= 已在 GSC 添加 property 并提交 sitemap | **只读**：空着就在每日报告里继续提醒 |
| 广告位1-SocialBar-code | global 位代码 | 回填「广告位管理」→ 注入 `app/layout.tsx` |
| 广告位2-NativeBanner-code | guide 位代码 | 回填「广告位管理」→ 注入 `GuideLayout.tsx` |
| 广告位3-todo-code | 第三个位占位 | **只读**：填了只提示，不处理 |
| 自动化状态 | **程序回写**：`已完成` / `待回填` / `待补填` / `失败`；空 = 这行还没填任何自动化项 | 每轮回填后按站点真实状态重算，只改变化的格子 |

> 2026-10-26：「站点」列改成写**裸域名**，原「域名」列已从两张表删除——两列内容本来就一样，
> 人看表时多一列反而累。程序按 `x.vercel.app → x` 反推目录名，所以表里不用再出现目录名。

`自动化状态` 的口径是**这一行做完没有**，不是「填了的东西落地没有」——
`已完成` 要求 GA4（两个 ID）+ 广告位1 + 广告位2 **全填且全上线**，
否则「只填了 GA」的行会被误标成做完（2026-10-26 踩过这个坑）。

| 值 | 含义 | 人工该做什么 |
|---|---|---|
| `已完成` | 三样都填了，且都已落到站点并上线 | 无事，这行收工 |
| `待补填` | 只填了一部分（还差 GA4 或某个广告位） | 把缺的补上，下轮自动回填 |
| `待回填` | 三样都填了，但还没落地（值有误 / 等下一轮 / 部署没成功） | 看 `.agent/ledger-sync-log.jsonl` 的 `badValues`，或等下一轮 |
| `失败` | 上次回填或部署失败 | 不用手改；下轮会**强制重新部署**该站 |
| 空 | 一个自动化项都没填（人工还没开始） | 照常填 GA4 / 广告位 |

想立刻知道「程序认不认我刚填的值」：`node scripts/sync-ledger-manual.mjs --status-only`
（只重算这一列，不改站点、不部署）。

### 8.3 每日 20:00 回填

- 调度：launchd `com.games-site.sync-ledger-manual`（本机 20:00，与 21:00/04:00 的
  auto-build 错开一小时，避免抢 Vercel 每日部署额度）
- 脚本：`node scripts/sync-ledger-manual.mjs --apply`（默认 dry-run，只出计划）
- 只处理**有变化**的站：值已和站点代码一致的行完全不动，也就不部署
- 每轮先把自动化表的 `上线日` 同步进人工表（新站补行时也一并带上），再回填 GA / 广告位
- 部署完**重读**「广告位管理」再回写 `自动化状态`（不能拿跑之前的内存状态算，那时还没上线）
- 上一轮标 `失败` 的站，即使文件已和台账一致，本轮也**强制重新部署一次**（否则值永远落不了地）
- `--no-deploy` 时不回写 `自动化状态`（没上线就标「已完成」是假的）
- 单次部署上限 `--max-deploy`（默认 10 站），超出的顺延到次日，不会一次性刷爆额度
- 落日志：`.agent/ledger-sync-log.jsonl`（每次一行：计划/部署/失败/顺延/GSC 未填）

### 8.4 MUST

MUST 人工值只填台账(人工)表，MUST NOT 同时手改站点代码和表（会互相覆盖）
MUST 每月滚动时用 `node scripts/roll-month-ledger.mjs --month YYYY-MM --apply` 一次建两张表
MUST NOT 手改表名（脚本按 `站点台账(自动化)|(人工)YYYY-MM` 解析；旧名 `站点台账2026-10` 只做兼容）
MUST NOT 手改 `上线日` / `自动化状态` 两列（程序每轮按自动化表与站点真实状态重算，手改会被覆盖）
MUST `站点` 列保持**裸域名**写法（`x.vercel.app`）；MUST NOT 改回目录名或加 `https://`——脚本靠它反推目录
MUST NOT 把 `[待确认]` 当值用：回填脚本会跳过，Dashboard 也读不出来
