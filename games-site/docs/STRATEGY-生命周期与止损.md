# 战略基线与站点生命周期

> 2026-10-25 定稿。对照「游戏站建站全流程清单」第 1 部分（一、前瞻战略）逐节点落地。
> 本文是**判断标准**，不是操作手册：操作走 `SOP-游戏攻略站上线.md`，执行走岗位卡。

---

## 一、我们做的是概率生意

参照 [袁锐钦：不会写代码，怎么做靠 Google 广告赚钱的游戏攻略站](https://scys.com/articleDetail/xq_topic/14425544145221552)
（开源流水线 [AnvilWiki](https://github.com/PNGTRID/AnvilWiki)，demo `anvilwiki.pages.dev`）：

- **单站成败不可预测**，靠"铺量 + 快速止损"把胜率兑现成收益。
- 所以战略的核心不是"把一个站做到最好"，而是**建立一套能批量判断、批量放弃的尺子**。
- 推论：判断标准必须**前置、可量化、可自动跑**，不能靠事后感觉。

我们与原帖的一个关键差异（必须写下来，否则会拿错尺子）：

| 项目 | 原帖口径 | 我们的口径 |
|---|---|---|
| 模式 | 单站精品，逐步扩到多站 | 45 站长尾矩阵，单站目标低 |
| 单站跑通线 | 3 个月后日 UV ≥ 50 | **30 天 PV ≥ 300**（约日 PV 10 / 日 UV 6） |
| 止损 | 3 个月后日 UV < 50 且无上升趋势 | **30 天 PV < 50 + 上线 ≥ 90 天 + 环比 < +30%** |

"日 UV 50" 换算成 30 天 PV 约 2,600（我们的 UV:PV ≈ 1:1.7）。若照搬原帖绝对值，
现有 45 站里 44 站都要砍——说明我们做的是**多站长尾**，不是单站精品。
两套尺子不能混用；本文的阈值按我们的模式校准，2027-01 复盘时再调。

## 二、三条时间线（D+30 / D+60 / D+90）

新站上线后按这三个检查点看，**每个点看的东西不一样**，不要用 PV 一个指标从头看到尾。

| 检查点 | 看什么 | 通过线 | 不通过说明什么 |
|---|---|---|---|
| **D+30** | 索引 | GSC 已收录页面占比 ≥ 50% | 技术问题（sitemap/robots/canonical/内容质量），先修技术 |
| **D+60** | 进词 | 至少 1 个页面有展示（GSC impressions > 0）或进入 Top 100 | 选题/词量问题，补页型，不是补外链 |
| **D+90** | 排名与点击 | 30 天 PV ≥ 50 且环比不为负 | 触发止损评估（见第三节） |

规则：

- **D+30 索引没过，不许进入扩充阶段**——先修技术，再谈内容。
- **D+60 进词没过，不许做外链**——词都没进，外链是浪费。
- **D+90 之前不做任何止损判断**——新站前 60 天数据天然难看，早砍会砍掉正在起量的站。

## 三、内容口径：页型 + 词数（不用「篇数」）

只数"篇数"会导致大量 400 词的水页。统一改为**页型 + 词数**双口径。

### 3.1 首批 5 类页型（候选池：只建有搜索需求的页型）

| # | 页型 | 说明 | 典型搜索意图 |
|---|---|---|---|
| 1 | **Codes**（兑换码） | 最新码 + 过期码 + 兑换步骤，带更新日期 | `{game} codes` |
| 2 | **Beginner / Getting Started** | 前 2 小时怎么玩、核心循环 | `{game} beginner guide` |
| 3 | **Tier List / Best Builds** | 角色/武器/职业排行 + 理由 | `{game} tier list` / `best build` |
| 4 | **核心机制 / Boss 攻略** | 卡点内容：某个 boss、某个系统怎么解 | `{game} {boss} how to beat` |
| 5 | **FAQ / Release 信息** | 发售时间、平台、联机、价格、是否 EA | `is {game} multiplayer` / `release date` |

### 3.2 数量与词数

| 项目 | 标准 |
|---|---|
| 首批页数 | **5–8 页**，5 类页型尽量各至少 1 页（无搜索需求的页型可跳过；原 SOP "至少 10 篇"作废） |
| 首批总词数 | **≥ 8,000 词** |
| 单篇词数 | **≥ 1,200 词**（FAQ 类可到 800，但同批平均仍要达 1,200） |
| 后续节奏 | 上线后 4 周内每周 **+5–10 页**（**D+30 下限 15–20 页**），之后按生命周期分级决定；补页优先于开新站（见 `docs/STRATEGY-内容生产.md` 第六节） |
| 单篇结构 | 问题式 H2；首段 40–60 词直接给答案；2–4 个表格；带 FAQPage 结构化数据 |

> 为什么要词数下限：AdSense / Google 对"薄内容站"的容忍度在下降，
> 且薄页进不了排名——现有 45 站里 30 天 PV = 0 的有 9 站，
> 它们的 GA 埋点正常（不是统计缺失），是内容量与竞争度的问题。

## 四、站点生命周期分级（A/B/C/D）

数据来源固定：**dashboard `/api/traffic`（GA4，30 天窗口 + 前一 30 天环比）+ 站点台账「上线日」**。
计算脚本：`scripts/lifecycle-report.mjs`。台账字段：`PV(30d)` / `PV 环比(%)` / `生命周期状态`。

| 分级 | 判定条件（自上而下，命中即停） | 动作 |
|---|---|---|
| **A 加码** | PV(30d) ≥ 300，**或** PV ≥ 100 且环比 ≥ +50% | 优先补页型、补长尾词、接广告（PV≥100 才接） |
| **B 维持** | 50 ≤ PV(30d) < 300 | 按周更节奏维护，不加码 |
| **C 观察中** | PV < 50 且（上线 < 90 天 **或** 环比 ≥ +30%） | 不动，等到 D+90 再判 |
| **D 不再维护** | PV < 50 且上线 ≥ 90 天 且 环比 < +30% | 停止投入 + 台账标记 `不再维护` |
| **不可判定** | 台账与 dashboard 都没有上线日 | 先补上线日，**不许当 0 处理** |

细则：

- **小基数保护**：环比 ≥ +50% 的加码条件要求 PV ≥ 100。3 PV → 5 PV 也是 +66%，但那是噪声。
- **环比必须真实**：脚本直接取 GA4 的 30 天 vs 前 30 天，不许估算；
  GA4 取不到数据时报"不可判定"，MUST NOT 当零流量。
- **上线日**：优先用台账；台账空时用 dashboard 的 git 首次提交日（报告中以 `*` 标注）。
- **D 档不是永久判决**：每季度复核一次，若 30 天 PV 回到 50 以上或环比 ≥ +30%，**恢复为观察中**。

## 五、止损 = 停止投入，不删站

D 档的归档动作**只有两条**：

1. **停止投入**：不再新增攻略、不再接广告、不再做关键词扩展、不再排 QA。
2. **标记**：台账 `生命周期状态` = `不再维护`，备注写清止损日期与当时数据。

**不做的事（MUST NOT）**：

- MUST NOT 删站、下架页面、跳转重定向——已收录页面仍可能带来零星流量和权重。
- MUST NOT 改代码、改模板（模板统一，改动会污染其他站）。
- MUST NOT 因为"看着难受"而提前砍站——D+90 之前一律观察。

### 组合层止损线

单站止损之外，另设一条**方法论止损线**：

> 若某批次新建站点中，**D 档占比 > 50%**，暂停建新站，先复盘选品与内容口径，
> 修好方法论再继续。理由是这时问题在方法，不在某个站。

## 六、产能与节奏

| 项目 | 标准 | 现状 |
|---|---|---|
| 新建站节奏 | **每天 ≥ 5 站**（≈ 每月 150 站） | 7 月建 23 站、8 月 15 站、9 月 4 站，**远低于铺量目标** |
| 单站人工时长 | ≤ 6 人工小时（不含 Agent 时间） | 待实测（D+30 回填台账） |
| 每站上线后 4 周 | 每周 +5–10 页 | 未执行，是当前最大缺口 |
| 部署额度 | Vercel 免费版 100 次/UTC 日 | **会成为瓶颈**：每天 5 站建 + 5 站发 ≈ 10+ 次部署/日，批量日需分批 |

节奏原则：

- **铺量优先**：每天 ≥5 站是硬下限，不达标说明流水线有卡点，要先修卡点而不是降目标。
- **内容下限不放松**：每站上线仍要过 5 类页型 / 总词数 ≥8,000 / 单篇 ≥1,200。
  每天 5 站≈每月 150 站，对应每月 ≥120 万词，必须 Agent 化生产 + QA 抽检，人工只做验收。
- **老站不追投**：45 个老站近一个多月没有维护，是 24 站环比下降的主因；
  按 D 档规则处理——能回升就留着，回不来就停止投入，不为了救老站拖慢新站节奏。

> 2026-10-25 调整：原「每月 ≤6 站」作废。此前的低建站量是为了配合人工审校，
> 现在改为流水线铺量，卡点从「建多少」变成「自动化率够不够」。

## 七、第 1 部分各节点的审核方式

「怎么审」= 看什么证据、谁看、多久看一次。没有证据的审 = 没审。

| # | 节点 | 审什么 | 证据 | 谁审 | 频率 |
|---|---|---|---|---|---|
| 1 | 路线选择（铺量） | 铺量是否还成立 | `lifecycle-report.md` 里 D 档占比；> 50% 触发方法论止损 | 主 Agent | 每季度 |
| 2 | 内容量标准 | 新站是否真达线 | QA 报告里的「页型 + 词数」表（逐页词数、页型覆盖） | QA 审核员 | 每站上线前 |
| 3 | 生命周期与止损线 | 分级是否可追溯 | 台账 `PV(30d)`/`PV 环比(%)`/`生命周期状态` 与报告一致；`不可判定` = 0 | 主 Agent 复核生命周期管理员 | 每月 |
| 4 | 模板差异化 | 暂缓，不审 | 只有一条决议记录：先用一套模板 | — | — |
| 5 | 产能与节奏 | 是否达标 | 每日新建站数（≥5）+ 台账「攻略数」的周增量 | 主 Agent | 每日 |

三条通用审核原则：

1. **证据链优先**：结论必须能指到具体文件/字段/脚本输出，不接受"感觉还行"。
2. **脚本先跑、人后看**：能自动算的都自动算，人只判断边界情况。
3. **异常必须显性**：取不到数据、缺上线日、台账缺行，都要在报告里单独列出，
   MUST NOT 静默按 0 或按正常处理。

## 八、执行链

```
每月 1 日：
  主 Agent 派发 → 生命周期管理员
    ├─ node scripts/roll-month-ledger.mjs --apply     # 建本月表（复制上月全量行）
    ├─ node scripts/sync-site-ledger.mjs --apply      # PV / 环比 回填台账
    ├─ node scripts/lifecycle-report.mjs --apply      # 分级报告 + 写生命周期状态
    └─ 交付 .agent/lifecycle-report.md（A/B/C/D 清单 + D 档止损建议）
  主 Agent 验收 → 对 D 档执行「停止投入 + 标记」，对 A 档排扩充
```

- 岗位：**生命周期管理员**（`docs/agents/20/21`），与 **性能监控员**（`15/16`，仍暂停）**分开**。
  性能监控员看趋势与异常，生命周期管理员出分级与止损结论；不合并，避免单岗位上下文过重。
- 日历：每月 1 日出报告；每季度末（3/6/9/12 月）复核 D 档，决定是否恢复。

## 九、月度台账（2026-10-25 起；2026-10-26 拆成两张）

站点台账**按月分表**，每月两张：

- **自动化表** `站点台账(自动化)YYYY-MM`：全量快照（全部站点 + 当月 PV/环比/分级），脚本读写
- **人工表** `站点台账(人工)YYYY-MM`：GA4 / GSC / 广告位代码，人写、脚本每天 20:00 回填（详见
  `docs/STRATEGY-域名与部署.md` 第八节）

分级只看自动化表；人工表不参与分级。

| 事项 | 做法 |
|---|---|
| 表名 | `站点台账(自动化)` + 年月：`站点台账(自动化)2026-10`、`站点台账(自动化)2026-11`…（旧名 `站点台账2026-10` 仅做兼容） |
| 当前表 | `站点台账(自动化)2026-10`（`tblTDpkA9odla8No`，46 行）＝ 2026-10 的记录；脚本按「当月表名」读写 |
| 建新月份表 | `node scripts/roll-month-ledger.mjs --month 2026-11 --apply` → 一次生成两张表（自动化表复制结构 + 全部站点行，PV/环比留空；人工表整行沿用上月） |
| 填数 | `node scripts/sync-site-ledger.mjs --apply`（默认写当月表，缺表会报错提示先建表） |
| 分级 | `node scripts/lifecycle-report.mjs --apply`（同默认当月表） |
| 历史月 | 只读，不再回写；需要对比时用 `--month 2026-10` 显式指定 |

缺当月表时脚本**直接报错**，不会退回去写上月表——避免把本月数据写进上月快照。
