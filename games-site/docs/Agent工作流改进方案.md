## 一、为什么我们的 Agent 工作总是出现问题

### 对照模板诊断

| 模板要求 | 我们的现状 | 出现的问题 |
|---------|-----------|-----------|
| **岗位卡**（输入/动作/输出/成功标准/兜底/不做） | ❌ 没有 — 每次临时写 prompt | 不同批次质量波动大，遗漏检查项 |
| **工作流卡片**（MUST 步骤 + 判断 + 异常处理） | ⚠️ 部分 — 有 PDCA 规则但不完整 | 修改 94% 时只改 1 个文件漏掉 5 个 |
| **Profile**（RFC2119 规则：MUST/SHOULD/MUST NOT） | ⚠️ 有零散规则但未集中 | "hands-on" 声明、"community consensus" 断言反复出现 |
| **测试证据链**（输入/过程/输出证据） | ❌ 没有 — 只报告 "build 通过" | 部署失败自己不知道，让 ChatGPT 看到旧版本 |
| **问题 → 规则闭环** | ⚠️ 有教训记录但未固化为 MUST 规则 | rootDirectory 问题反复出现 3+ 次 |

### 具体问题案例回放

| # | 案例 | 根因 | 模板中对应的缺失环节 |
|---|------|------|---------------------|
| 1 | 修改 94% 漏改 5 个文件 | 没有「全局搜索 MUST」规则 | 工作流的「判断点」未挖掘 |
| 2 | 部署后未验证线上，误判 ChatGPT 看的是缓存 | 没有「部署后 MUST 线上验证」规则 | 测试证据链缺失 |
| 3 | GA4 凭据误判「未配置」 | 没有「区分本地读不到 vs 不存在」规则 | Profile 缺判断依据 |
| 4 | 关键词量当成流量推荐站点 | 没有「用真实数据 MUST」规则 | 工作流缺验证步骤 |
| 5 | rootDirectory 反复叠加 | 旧脚本为「假设的未来」保留恢复步骤 | 「本期不做」边界缺失 |
| 6 | Phase 1 批量改漏 Privacy/Terms 矛盾 | 没有「法律页面一致性 MUST 检查」 | 成功标准不完整 |
| 7 | 子 Agent 质量波动 | prompt 每次临时写，无固定岗位卡 | 岗位卡缺失 |
| 8 | 跨站污染（dwarfdelve 硬编码 grainrot 域名） | 没有「域名/商标 MUST 全局检查」 | 自检规则缺失 |

## 二、借鉴方案

### 方案 1：建立「内容合规审计员」岗位卡

按模板四步法给我们的核心工作定岗位：

```
## Agent 岗位卡

### 岗位名称
内容合规审计员

### 一句话岗位定义
当收到一个游戏站点目录时，自动审计并修复 AdSense 合规问题
（事实核验 + 断言降级 + 证据标注），并输出审计报告

### 输入
- 站点目录路径（如 games-site/sephiriawiki/）
- 可选：特定检查范围（P0/P1/P2 级别）

### 处理动作
1. 读取全部攻略 + 信任页面 + 配置文件
2. 事实核验：Steam 商店页交叉验证（价格/评分/开发商/系统要求）
3. 断言扫描：搜索 "community consensus" / "safest" / "best" / 绝对化表述
4. 全局搜索：修改任何数据前 MUST 搜索全站引用
5. 修复：按 P0→P1→P2 优先级执行
6. 构建 + 部署 + 线上 curl 验证

### 输出
- 审计报告（问题清单 + 严重度 + 修复结果）
- 修改后的站点文件

### 成功标准
- 线上 curl 验证通过（MUST 提供验证证据）
- 无残留断言/旧数据/矛盾声明
- 构建零错误

### 人工兜底
- 无法验证的事实 MUST 标记 [待确认]，MUST NOT 猜测
- 涉及版权/商标/法律判断时暂停问人
- 部署失败 2 次后暂停，报告原因

### 本期不做
- 不新增攻略、不合并文章（除非明确授权）
- 不加 "I tested this" 类无法支撑的经验声明
- 不动非目标站点的文件
```

### 方案 2：把散落规则固化为 Profile（MUST/MUST NOT）

把我们会话中总结的所有教训写成 RFC2119 规则，集中到一处：

```markdown
## 内容合规审计员 Profile（规则部分）

### 事实核验
MUST 修改任何数字/名称/机制前，先 WebFetch 线上实际内容
MUST 系统要求/价格/评分与 Steam 商店页一致，或注明来源
MUST NOT 写 "Patch X.XX" 除非有官方 patch notes 链接
MUST NOT 写固定评分数字（如 94%）— 用 "Very Positive (checked date)"
MUST NOT 用 "community consensus" 包装编辑判断

### 修改执行
MUST 修改全站性数据前 grep -rn 全局搜索所有引用文件
MUST 修改后 npm run build 零错误
MUST 部署后用 curl 验证线上内容已更新
MUST NOT 假设「本地文件 = 线上内容」

### 信任页面
MUST 检查 Privacy/Terms 中 AdSense 声明与实际状态一致
MUST 检查 Footer/About 的商标/开发商名称正确
MUST 检查 JSON-LD 中域名无跨站硬编码

### 部署
MUST 部署前确认 rootDirectory 为空（CLI 模式）
MUST NOT 恢复 rootDirectory（Git 集成未启用）
部署失败 2 次 MUST 停止并报告

### 报告
MUST 输出审计报告（问题/严重度/修复/证据）
MUST 提供验证证据（build 输出 + curl 结果）
```

### 方案 3：测试证据链（每次修改闭环）

每次修改必须留证据：

| 环节 | 证据 |
|------|------|
| 修改前 | 线上 curl/WebFetch 输出（确认问题存在） |
| 修改后 | build 输出（零错误） |
| 部署后 | 线上 curl 验证（确认修复生效） |

### 方案 4：接力规范（主 Agent ↔ 子 Agent）

按 08-接力模板，主 Agent 派发子 Agent 时用固定格式：

```text
任务编号：BATCH-XX
材料版本：当前 main 分支
工作背景：（为什么做这件事）
请完成：（具体任务）
完成标准：（可验证的验收标准）
停止条件：（遇到什么情况必须停下）
MUST NOT：（明确边界）
```

## 三、落地计划

| 步骤 | 内容 | 文件 |
|:--:|------|------|
| 1 | 岗位卡 | `docs/agents/01-岗位卡-内容合规审计员.md` |
| 2 | Profile 规则库 | `docs/agents/02-Profile-内容合规审计员.md` |
| 3 | 把 Profile 集成到 CLAUDE.md | `games-site/CLAUDE.md` 引用 |
| 4 | 下次派发子 Agent 时用接力格式 | 直接生效 |

**预期效果**：
- 子 Agent 质量稳定（固定岗位卡替代临时 prompt）
- 同类问题不再复发（问题→规则闭环）
- 验收有据可查（证据链）
