## 三、可优化环节（按 ROI 排序）

1. **交付不可见（最大问题）** — 日报只落日志。需要 T1「每日交付表」：一行 = 一站一天，带线上 URL、
   验证结果、commit。
2. **QA 黄项没有闭环** — 写完沉在 md 里，靠下次 deep QA 重扫，无法回答「上周那 8 个黄项修了没」。
   需要 T2 状态机：待修 → 已修待部署 → 已部署待复验 → 关闭。
3. **事实基线缺失** — 每站的「当前版本 / 玩家上限 / 发售状态」在每篇文章里各写一遍。
   2026-10-24 修的 12 篇里 4 篇是版本漂移（Aincrad 1.0.6、Witchspire 0.3.2、Sephiria 1.0.33、
   SpiritVale 0.34.2），另有 grainrot 正文 1.13 / FAQ 1.09 自相矛盾。根因是没有基准值。→ T3。
4. **校验靠自觉，没有闸门** — `related` 内联数组导致 587 篇「相关攻略」静默不渲染。
   可自动拦截：related 必须块状、`updated` 必须 ISO、正文 800–1600 字、sources ≥2 且≥1 条 Official、
   内链 slug 必须存在。
5. **部署验证与配额无账本** — `pending-deploys-*.md` 是应急产物；100 次/天额度没有计数。→ T5。
6. **数据断供** — `ga4-pv-rank.mjs` 缺 `client_email`，扩充名单还是 2026-09-02 的 PV 快照。
7. **Agent 判断标准不统一** — QA 因本机打不开 Steam 两次误判「来源虚假」（Grain Rot、Tears of Metal，
   已用 ISteamNews 证伪）。需区分「证据矛盾」与「本机不可达」，后者标 `[Unverified-Offline]` 且不阻断。
8. **人工检查点不明确** — 「≥15 分自动建站」「P0 自动修完直接发」，人只在事后。

## 四、设计原则

1. **仓库仍是唯一事实源** — 站点正文永远在 git，飞书不放正文副本，避免双写漂移。
2. **飞书只放元数据 + 链接** — live URL / 文件路径 / commit。
3. **字段分「机器写」与「人写」** — 机器只 upsert 自己的列，**永不覆盖人写列**。
   幂等键：`(日期, 站点)` 或 `(站点)`。
4. **表格负责「查」，文档负责「讲」** — Bitable 做过滤/状态/逾期；Doc 只做每日摘要与月度复盘。

工具链：`lark-cli`（已装，`base` / `sheets` / `docs` / `wiki` 四个域）。
新增 `scripts/feishu-report.mjs` 走 Bitable 写入。

## 八、风险与注意

- **应用权限**：wiki 空间内新建 Base 需要应用具备 `wiki:wiki` / `wiki:space:retrieve` 等权限，
  并把应用加为该空间成员。若机器人身份不可写，退路是在应用自有云空间建 Base 后人工挂进 wiki 空间。
- **身份**：`lark-cli` 当前只有 bot 身份（user 身份未登录）。所有写入走 bot，返回的
  `permission_grant` 要确认人可打开。
- **Vercel 配额**：免费版 100 次/日（UTC 日切，北京时间约 08:00 重置）。T5 的「当日已用部署次数」
  必须在 80 次时告警，避免再次撞满。
- **不双写**：任何内容一旦进入 git，飞书只存引用；反向同理，飞书里的人工判断不回写正文。
