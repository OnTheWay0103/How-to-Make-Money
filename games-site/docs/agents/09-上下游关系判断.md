## 一、当前 Agent 体系（4 岗位）

| Agent | 收到什么 | 完成什么 | 交付什么 |
|-------|---------|---------|---------|
| 主 Agent（统筹） | 用户指令 | 拆解/派发/验收/部署/闭环 | commit + 状态报告 |
| 内容合规审计员 | 站点目录 + 检查级别 | 事实核验 + 断言清理 + 证据标注 | 审计报告 + 修改文件 |
| 建站协调员 | 建站任务（定时/手动） | 选品→建站→配置 | 新站点 + QA 材料 |
| QA 审核员 | 新建/扩充的攻略 | 残留扫描 + 编造检查 | QA 报告（PASS/FAIL） |

## 二、上游（输入从哪来）

| Agent | 上游来源 | 入口 | 触发时机 |
|-------|---------|------|---------|
| 主 Agent | 用户（人） | Claude Code 会话 | 用户发消息 |

| QA 审核员 | 建站协调员产出 | QA 报告请求 | 每次建站后 |

## 三、下游（结果谁用）

| Agent | 下游 | 结果用途 |
|-------|------|---------|
| 主 Agent | 用户 | 查看进度/决策 |
| 合规审计员 | 主 Agent | 验收 → commit → 部署 |
| 建站协调员 | QA 审核员 | 审核 → PASS 才部署 |
| QA 审核员 | 主 Agent / 部署流程 | PASS 放行 / FAIL 退回 |

## 四、完整工作链（三条链路）

```
链路 A（建站，当前暂停）:
选品调研(工具harvest) → 建站协调员(Agent) → QA审核员(Agent) → 部署(主Agent) → STATS更新

链路 B（AdSense 合规，活跃）:
用户(人) → 主Agent(拆解) → 合规审计员(Agent) → 主Agent(验收) → commit/deploy → 线上验证

链路 C（日常维护）:
用户(人) → 主Agent → (单点直改 or 子Agent) → 验收 → 部署
```

## 五、各环节由谁完成

| 环节 | 承担者 | 类型 |
|------|--------|------|
| 关键词采集 | harvest 脚本 | 工具 |

| 建站 | 协调员 | Agent |
| QA | QA 审核员 | Agent |

## 六、环节之间的关系

| 关系 | 环节对 | 类型 |
|------|--------|------|
| 建站协调员 → QA 审核员 | 前后交接（产出→审核） | ✅ 稳定 |
| QA 审核员 → 部署 | **先判断再分流**（PASS 部署 / FAIL 退回） | ✅ 稳定 |
| 合规审计员 → 主 Agent | 前后交接（报告→验收） | ✅ 稳定 |
| 主 Agent → 用户 | 人工确认（对外操作决策） | ✅ 必须 |

## 七、本轮判断：**连接**

选择连接的 Agent↔Agent 交接：**建站协调员 → QA 审核员**

理由：
1. 输入输出格式稳定（站点目录 → QA 报告）
2. 有明确的 PASS/FAIL 分流规则
3. 是唯一的生产流水线交接（其他都是主 Agent 中介）

## 八、交接规范

**前一个 Agent（建站协调员）交什么：**
- 新站点目录路径
- 新增/修改的攻略文件列表
- 建站评分依据（选品卡片）

**后一个 Agent（QA 审核员）怎样检查：**
- 按 Profile 执行：residue 扫描 + 内容抽样 + 编造检查
- 输出 QA 报告：每站 PASS/FAIL + 具体问题位置
- FAIL 站点 MUST 退回协调员修复（编造内容）或转合规审计员（断言问题）

## 九、⚠️ 发现的问题：QA 审核员 vs 合规审计员职责重叠

两个岗位都做「事实核验」和「编造检查」。按模板第 7 条（检查职责重复），需重新划分：

| 任务 | QA 审核员（建站时） | 合规审计员（改造时） |
|------|:--:|:--:|
| 新站部署前的编造检查 | ✅ 负责 | ❌ |
| 旧站 AdSense 合规改造 | ❌ | ✅ 负责 |
| 抽查 Steam 事实一致性 | ✅ 建站时 | ✅ 改造时 |
| 断言降级 + 证据标注 | ❌ 只报告 | ✅ 执行修复 |

**结论**：保留两个岗位，但明确边界——QA 是「建站流水线的质量门」，合规审计员是「存量站点的改造执行者」。QA 只报告不修复；审计员既报告又修复。

## 十、哪一步需要人确认

1. **AdSense 申请**：必须用户手动提交（已按此执行）

3. **大改方案**（合并文章/删除内容）：需用户确认
4. **对外发布**：任何对外声明需用户确认
