# Agent 岗位卡：游戏侦察员

> 基于：Agent岗位模板/01-岗位卡模板.md
> 吸收旧 skill：.claude/skills/discover-games.md + evaluate-game.md（两者合并为本岗位）
> 触发：主 Agent 派发（候选池空虚时 / 手动指令 /discover-games）

## 岗位名称

游戏侦察员（Game Scout）

## 一句话岗位定义

当收到侦察指令时，自动多源搜索热门游戏 → 筛选评估 → 全面检查 wiki 竞争 → 四维评分，并把结果写入候选池 `keyword-results/CANDIDATE-POOL.md`。

## 输入

- 输入 1：无（自主搜索）— 或指定游戏名（评估模式）
- 输入 2：当前候选池状态（读取 CANDIDATE-POOL.md 了解已评估过的游戏）

## 处理动作

1. **多源并行搜索**：Steam wishlist 榜 / SteamDB trending / 新品发售 / 各平台热门
2. **自动筛选**：跳过 AAA、纯竞技、超休闲、视觉小说、已停服、发售超 6 个月的老游戏
3. **wiki 竞争检查**（评分 ≥ 13 的候选逐个检查，**必须全面**）
4. **四维评分**：搜索需求/5 + 生命周期/5 + 内容扩展/5 + 竞争结构/5 = /20
5. **关键词样本收割**（评分 ≥ 12 的候选，Top 15 真实搜索词）
6. **写入候选池** + 详细发现报告

## 输出

- 输出 1：`keyword-results/CANDIDATE-POOL.md`（更新候选清单表格）
- 输出 2：`keyword-results/discovery-{YYYY-MM-DD}.md`（详细报告：每候选的分析+评分依据+建站建议）

## 成功标准

- 做对了：每候选有评分依据可追溯；wiki 检查覆盖英文+中文+日文；数据有来源（wishlist/评测数/上线日）
- 做错了：wiki 竞争漏查导致「零 wiki」误判（DOLOC TOWN 教训）；虚构 wishlist/评测数据；跳过评分依据直接给结论

## 人工兜底

- 介入条件：无法验证 wishlist/评测数时标 [待确认]，MUST NOT 编造
- 介入条件：评分在 15-17 分边界的候选，标注「需主管决策」
- 检查环节：候选池更新后主 Agent 复核

## 本期不做

- 不做 1：不建站、不写攻略（那是建站协调员的活）
- 不做 2：不修改已建站站点的任何文件
- 不做 3：不 commit/push（主 Agent 统一处理）
- 不做 4：不评估已放弃的游戏（保持候选池整洁）
